## Accès Supabase et marche à suivre Free

L'API Supabase confirme une seule organisation accessible, `TESKA SAS`, plan Pro, avec les trois projets existants YOUMGO, Youmbia et anivia. Aucun autre projet ne doit être réutilisé. Le connecteur ne fournit pas les rôles de l'utilisateur dans l'organisation ni le décompte des projets Free où il est Owner/Admin. L'éligibilité réelle est donc indéterminée; aucune organisation ni aucun projet n'a été créé.

Pour vérifier manuellement sans accepter un coût : ouvrir le Dashboard Supabase, le sélecteur d'organisation, puis **New organization**; sélectionner **Free**; vérifier que le récapitulatif affiche 0 $; arrêter si l'écran propose uniquement un plan payant ou indique que le quota de projets Free est épuisé. Les règles actuelles accordent deux projets Free actifs au niveau du compte, agrégés à travers ses organisations où il a le rôle Owner/Admin; une organisation peut être Free séparée d'une organisation Pro. Les limites Free incluent 500 MB DB par projet, 5 GB egress, 1 GB stockage, 500 000 invocations Edge Functions, 50 000 MAU, 2 M messages Realtime et 200 connexions simultanées. Un projet peu actif peut être mis en pause après sept jours. Sources : [facturation Supabase](https://supabase.com/docs/guides/platform/billing-on-supabase), [FAQ facturation](https://supabase.com/docs/guides/platform/billing-faq), [pause des projets Free](https://supabase.com/docs/guides/platform/free-project-pausing).

## EAS, Firebase et Apple — préparation des actions console

`eas.json` garde les deux profils QA en `development`/`preview`, avec UUID placeholder bloquant. Les identifiants Android/iOS restent `com.youmbia.mobile.dev`; les schemes restent distincts. Le garde refuse le ref Supabase production, un URL/ref incohérent, un projet EAS partagé, des variables obligatoires absentes et un fichier Firebase du mauvais projet/package. Aucun profil QA n'a de valeur de remplacement issue de production. L'UUID QA doit être celui renvoyé par le nouveau projet EAS.

Pour Firebase, enregistrer exactement `com.youmbia.mobile.dev`, activer FCM HTTP v1, télécharger le `google-services.json` du projet QA et contrôler le `project_info.project_id` ainsi que le client Android. Dans **le projet EAS QA seulement**, ajouter le fichier QA comme variable File et téléverser le JSON du compte de service sous les credentials Android FCM v1. La clé privée reste hors Git et hors sortie terminal. FCM est sans coût sur Firebase Spark; ne pas lier de compte de facturation ni activer des produits Google Cloud payants. Sources : [tarifs Firebase](https://firebase.google.com/pricing), [credentials FCM v1 avec Expo](https://docs.expo.dev/push-notifications/fcm-credentials/), [environnement serveur FCM](https://firebase.google.com/docs/cloud-messaging/server-environment).

Pour iOS, un Account Holder/Admin Apple doit confirmer Push Notifications sur l'App ID explicite existant `com.youmbia.mobile.dev`. Si la capacité est inactive, l'activer et sauvegarder; créer/renouveler le provisioning profile après ce changement; configurer une clé APNs partagée ou dédiée dans EAS, en l'attachant au projet QA seulement. Ne pas créer un deuxième App ID sans nécessité. Apple documente l'activation de capacité sur l'App ID et l'entitlement APNs dans [Register an App ID](https://developer.apple.com/help/account/identifiers/register-an-app-id/) et [Registering your app with APNs](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns).

Le dispatcher applicatif envoie vers Expo Push API avec `EXPO_ACCESS_TOKEN`; la clef FCM v1 et la clé APNs doivent être des credentials EAS QA distincts. Les secrets Supabase QA requis pour le dispatcher/scheduler (dont `TRANSACTIONAL_PUSH_DISPATCH_SECRET`, `EXPO_ACCESS_TOKEN`, cible de service et URL QA) ne seront définis qu'après l'existence et la revue du projet QA. Worker et scheduler restent OFF à l'installation.

1. Owner Supabase confirme rôle, quota Free et 0 $ sur l'écran **New organization**; création manuelle d'une organisation Free YOUMBIA QA.
2. Une fois l'écart de migration fermé par l'équipe backend, autorisation distincte de créer le projet Supabase Free QA et de le peupler uniquement de schéma/données fictives.
3. Owner Expo crée `youmbia-mobile-qa`; DevOps associe les seules valeurs QA puis vérifie la résolution statique Android/iOS.
4. Owner Firebase crée Firebase QA Spark et son app `.dev`, puis ajoute `google-services.json` et le credential FCM v1 dans le projet EAS QA.
5. Account Holder/Admin Apple vérifie ou active Push sur `.dev`; Owner Expo configure la signature, le provisioning et APNs du projet EAS QA.
6. Rejouer le gate SQL/RLS et tous les contrôles de configuration sur le SHA final; obtenir ensuite un GO séparé avant tout build. Les builds, migrations distantes et envois réels restent interdits dans le présent audit.
